# 관련 논문 분류표: 센서 · 구성 · eye-in-hand · 학습기반 · 촬영 장수

이 문서는 [`2023plus_calibration_review.md`](2023plus_calibration_review.md)에 정리한 논문 25편과 고전 baseline 6편을,
**우리 실험 조건과 직접 맞대볼 수 있는 5개 축**으로 다시 분류한 것이다. 기존 리뷰는 "정확도 수치"가 축이고,
이 문서는 "**어떤 장비로, 어떤 배치에서, 몇 장 찍어서**"가 축이다.

작성일 2026-09-16. 원문에서 확인하지 못한 항목은 빈칸으로 두지 않고 `미확인`으로 표시했다. 추정해서 채우지 않았다.

## 0. 용어 정의 (표를 읽기 전에)

이 문서에서만 쓰는 약칭이 아니라, 표의 모든 칸이 같은 뜻으로 읽히도록 미리 못박는다.

| 용어 | 뜻 |
|---|---|
| **고정 카메라 (EoB)** | 작업공간에 삼각대·프레임으로 **고정**된 카메라. eye-on-base 또는 eye-to-hand라고도 부른다 |
| **손목 카메라 (EiH)** | 로봇 팔 끝(그리퍼/플랜지)에 **붙어서 같이 움직이는** 카메라. eye-in-hand |
| **EIH 보정 여부** | 그 논문이 손목 카메라의 변환($T^G_C$)을 **실제로 추정하는지**. 단순히 "가능하다"고 언급만 한 경우는 `언급만`으로 구분 |
| **구성 유형** | 아래 4가지 중 하나. 이 축이 우리와 가장 크게 갈린다 |
| **학습기반** | 신경망·파운데이션 모델을 **보정 파이프라인 안에서** 쓰는가. 마커 검출기(AprilTag/ChArUco)는 학습기반으로 세지 않는다 |
| **촬영 장수** | 실제 장비(실촬영) 기준. 시뮬레이션 장수는 따로 `(sim)`으로 표기 |

**구성 유형 4분류**

| 코드 | 뜻 | 우리와의 거리 |
|---|---|---|
| **RM** | 로봇 + **여러 대** 카메라를 함께 보정 (robot + multi-camera) | **우리와 같은 부류** |
| **R1** | 로봇 + **한 대** 카메라 (전통적 hand-eye) | 카메라끼리의 교차검증이 없음 |
| **CM** | **카메라끼리만** 보정. 로봇 없음 (multi-camera only) | 고정카메라 그룹 부분만 비교 가능 |
| **RS** | 로봇 + 카메라가 아닌 **다른 계측기** (레이저트래커, 구조광 스캐너) | 정확도 상한 논의용 |

## 1. 우리 프로젝트의 기준선

먼저 우리 값을 확정해야 표의 다른 줄을 비교할 수 있다. 저장소 실제 설정에서 읽은 값이다.

| 축 | 우리 값 | 근거 |
|---|---|---|
| 센서 | **Intel RealSense D415 × 3 (고정) + D435 × 1 (그리퍼)**, color 1280×720 @ 15 fps | [`intrinsics/device_map.json`](../intrinsics/device_map.json), [`intrinsics/cam*.npz`](../intrinsics/) |
| 구성 유형 | **RM** — 고정 카메라 여러 대 + 로봇을 한 최적화에 통합 | [README §2](../README.md) |
| EIH 보정 | **한다.** $T^G_C$를 자유변수로 추정 (`gripper_cam_idx=2`) | [README §2](../README.md) |
| 학습기반 | **아니다.** raw corner pixel 재투영 최적화 (soft_l1, f_scale=2 px) | [`calibration_pipeline/reprojection.py`](../calibration_pipeline/reprojection.py) |
| 촬영 장수 | **45 event** (= 사전에 정한 촬영 시도 위치 수). event 하나마다 카메라 4대가 동시 촬영 → **이미지로는 최대 180장** | [CAPTURE_PROTOCOL.md](../CAPTURE_PROTOCOL.md) |
| intrinsic | ChArUco로 사전 재보정 후 **고정** (재투영 0.32~0.36 px) | [`intrinsics/charuco_intrinsics_report.json`](../intrinsics/charuco_intrinsics_report.json) |

> **장수를 셀 때 주의.** 논문마다 "images", "poses", "frames", "sets"를 섞어 쓴다.
> 로봇 자세 1개 × 카메라 N대 = 이미지 N장이므로, **자세 수와 이미지 수를 같은 칸에 놓고 비교하면 안 된다.**
> 아래 표는 원문이 쓴 단위를 그대로 적고, 단위를 괄호로 밝혔다.

## 3. 센서 비교: RealSense가 아닌 장비는 얼마나 좋고 얼마나 비싼가

요청하신 축이다. **RealSense를 기준선(1×)으로 두고** 상대적으로 적었다.
가격은 모델별 공개 정보가 제각각이라 **검증된 값과 대략값을 구분해서** 표시했다.

**기준선 — Intel RealSense (우리 장비)**

| 모델 | 방식 | 깊이 정확도 (공식 스펙) | 가격 |
|---|---|---|---|
| D415 (우리 고정 3대) | 능동 스테레오 | 2 m에서 오차 2% 미만 | 신품 기준 약 20~35만 원대 |
| D435 (우리 손목 1대) | 능동 스테레오, 광각 | 2 m에서 오차 2% 미만 | 약 25~40만 원대 |
| D455 | 능동 스테레오 | **4 m에서 오차 2% 미만** | 리퍼 $320 확인, 신품 약 50~60만 원대 |
| L515 | LiDAR | 약 5~14 mm (거리·반사율 의존) | 단종. 출시가 $349 |

> **중요:** 우리 파이프라인은 **RGB 코너의 픽셀 재투영**으로 푼다. 즉 위 표의 **깊이 정확도는 우리 최종 정확도를 직접 지배하지 않는다.**
> RealSense를 쓰는 진짜 비용은 깊이가 아니라 **color 해상도 1280×720과 렌즈 품질**이다.
> 아래 산업용/계측용 카메라와의 차이도 대부분 여기서 난다.

**RealSense가 아닌 센서 (논문에서 실제로 쓰인 것만)**

|---|---|---|---|---|

| **OptiTrack Flex 13** | C8 | **3D 재구성 sub-mm** (검증 wand 0.42 mm). 단, **반사 마커만** 보고 일반 물체는 못 본다 | **대당 $1.5K (약 200만 원)**, 최소 4대 + 소프트웨어 → **시스템 기준 10~20배** | 우리의 **독립 GT 장비 후보**이지 보정 대상 센서가 아님 |
| **Qualisys Arqus A12 / Miqus M3** | C1 (검증용) | 12 MP IR mocap, sub-mm | 공개가 없음. 대당 1천만 원 이상으로 알려짐 → **30배 이상** | 같은 이유로 GT 장비 |
| **Leica AT960 + T-Mac** | R12 | **6DoF를 ±15 µm + 6 µm/m 수준으로 측정** — RealSense보다 두세 자릿수 정확 | 1억 원대 → **300배 이상** | R12의 0.342 mm는 **이 장비가 있어야 나오는 수치**. 우리 2~3 mm와 같은 선에 놓을 수 없다 |
| **LMI Gocator 3210** | R14 | 구조광 스캐너, 수십 µm 급 형상 계측 | 수천만 원 → **100배 이상** | R14의 0.373 mm도 같은 맥락 |
| **CMM** | C9 | 계측실 기준기. 0.030 mm LME | 억대 설비 | 절대 기준 |
| **산업용 카메라 3대** | R15 | 모델 `미확인` | `미확인` | 1 mm 미만 주장의 전제를 확인 못 함 |

### 3.1 이 표에서 나오는 결론 3가지

1. **우리보다 작은 mm를 보고한 논문은 대부분 센서가 다르다.** R12(레이저트래커), R14(구조광 스캐너), C8/C9(mocap·CMM)는
   RealSense보다 **두세 자릿수 정확한 계측기**로 얻은 값이다. "논문이 0.37 mm인데 우리는 2~3 mm"는 **같은 축의 비교가 아니다.**
2. **RGB 카메라만 쓰는 논문 중 우리보다 확실히 좋은 센서는 R5(IDS 5 MP)와 R3(Hikvision 6 MP)뿐이다.**
   둘 다 **깊이 없는 고해상도 RGB**다. 우리 방법이 깊이를 안 쓰므로, **화소수만 올리는 업그레이드**가 비용 대비 효과가 가장 크다.
3. **RealSense를 쓴 논문(R7, R8, R9, R11, R6 일부)은 전부 카메라가 1~2대**다.
   **RealSense + 고정 여러 대 + 손목 1대**를 한 번에 푸는 조합은 이 표에 우리 말고 없다.

## 4. 축별 요약

### 4.1 구성 유형별

| 유형 | 해당 논문 | 편수 |
|---|---|---|
| **RM** (로봇 + 멀티카메라) — **우리 부류** | R1, R2, R3, R9*, R10, R13, R15, D1 | 8 |
| **R1** (로봇 + 카메라 1대) | R4, R5, R6, R7, R8, R11 | 6 |
| **CM** (카메라끼리만) | C1~C9 | 9 |
| **RS** (로봇 + 비카메라 계측기) | R12, R14 | 2 |

\* R9는 카메라 2대지만 **둘 다 손목**이라 고정 카메라 네트워크가 없다. 우리 구성과 다르다.

### 4.2 EIH(손목 카메라)까지 보정하는 논문 — **여기가 가장 얇다**

| 실제로 EIH를 추정 | 비고 |
|---|---|
| **R3** (Zhou, TIE'24) | 손목 3 + 고정 2. **고정·손목 혼합을 한 그래프에서 푸는 유일한 선행연구** |
| **R9** (Calib3R) | 전부 손목. 고정 카메라가 없음 |
| **R8** (EasyHeC++) | EiH로 확장하나 카메라 1대, 초기 자세는 수동 |
| **R6** (Kalib) | EoB·EiH 통합 정식화. 단 **손목 카메라는 자기 손을 못 보므로 우리 구성엔 적용 불가** |
| **R5, R11, R14, R10** | EiH이지만 **카메라 1대** 또는 카메라가 아님 |
| **ours** | **고정 3 + 손목 1을 한 최적화에서 동시에** |

> **정리:** "고정 카메라 여러 대 + 손목 카메라"를 **하나의 최적화로 푸는** 논문은 **R3 하나뿐**이고,
> R3는 산업용 RGB 카메라 5대에 UR 3대를 쓰며 **참값을 측정하지 못해 폐루프 오차로만 평가**했다.
> 우리가 외부 GT로 평가하면 이 칸이 실제로 비어 있다. **기여 주장의 근거로 가장 강한 축이다.**

### 4.3 학습기반 여부

| 학습기반 (5편) | 무엇을 학습 모델로 대체했나 |
|---|---|
| R6 Kalib | SpatialTracker로 **마커 없이** 기준점 추적 (zero-shot) |
| R7 EasyHeC | PointRend·PVNet으로 로봇 팔 마스크 (각 10,000장 학습) |
| R8 EasyHeC++ | SAM·GroundedSAM·DKM (로봇별 재학습 불필요) |
| R9 Calib3R | MASt3R/DUSt3R/VGGT pointmap |
| C3 | 사전학습 3D human pose |

**나머지 26편은 전부 비학습(기하 최적화)이다.** 우리도 비학습이다.
학습기반 5편의 공통점은 **마커를 없애는 것이 목적**이지 정확도를 올리는 것이 목적이 아니다 —
R9는 marker 기반 Evangelista보다 오히려 오차가 크고(6.91 mm vs 15.12 mm), R6은 기존 데이터셋 보정보다 IoU가 낮다.

### 4.4 촬영 장수 — 오름차순

| 장수 | 논문 | 단위 |
|---|---|---|
| 5~10 | R9 Calib3R ("10장 미만에서도"), R11 PlaneHEC (최소 5 set) | 자세 |
| 10 미만 / 15 | **R2 Allegro 산업 실험** | 이미지 |
| 10~20 | R6 Kalib (ablation) | frame |
| 15 / 25 | R9 (UR / Franka) | 자세 |
| **25** | **R5 Ulrich** | 자세 |
| 20 자세 / 100장 | R7, R8 (Baxter) | 자세 / 이미지 |
| **45** | **ours** | **event** (= 카메라 4대 동시촬영 → 최대 180장) |
| 45 고정점 × 20회 | C6 | 재구성 반복 |
| 99 | R12 (검증 전용) | data pair |
| 300 | R11 (수집 총량), R6 (sim) | set / frame |
| 약 1,000 | C8 | frame |
| 10,000+ | D1 METRIC | 이미지 (데이터셋 전체) |

**해석 두 가지.**

- 우리 45 event는 **로봇 포함 보정 논문 중 많은 편**이다. R2는 15장, R5는 25 자세로 끝낸다.
  즉 **"장수가 부족해서 오차가 크다"는 반론은 성립하지 않는다.**
- 반대로 **장수가 많은 쪽(C8 1,000 frame, D1 10,000장)은 전부 로봇이 없거나 데이터셋 논문**이다.
  로봇을 움직여 찍는 비용 때문에 로봇 포함 논문의 장수는 구조적으로 수십 개대에 머문다.

## 5. 우리 조건과 정확히 겹치는 논문이 있는가

5개 축을 모두 걸었을 때 남는 논문을 센 것이다.

| 조건 | 통과 논문 |
|---|---|
| RM (로봇 + 멀티카메라) | R1, R2, R3, R10, R13, R15, D1 |
| ＋ EIH도 보정 | **R3** |
| ＋ 소비자급 RGB-D 센서 | **없음** (R3은 산업용 6 MP RGB) |
| ＋ 비학습 픽셀 재투영 | R3 (해당), 단 폐루프 평가만 |
| ＋ 독립 외부 GT로 평가 | **없음** |

**결론: 5축을 모두 만족하는 선행연구는 없다.** 가장 가까운 것이 R3 하나이고, R3는 센서 등급이 다르고 독립 GT가 없다.
다만 이것은 **"우리가 더 정확하다"는 뜻이 아니라 "이 조합을 같은 평가로 잰 사람이 없다"**는 뜻이다.
정확도 주장은 여전히 [`SOTA_Claim_Protocol.md`](../SOTA_Claim_Protocol.md)의 절차를 따라야 한다.

## 7. 이 표에서 바로 나오는 실행 항목

1. **센서 업그레이드를 검토한다면 깊이가 아니라 화소수다.** 우리 목적함수가 RGB 코너 픽셀이므로,
   Hikvision MV-CE060-10UC(6 MP) 급으로 고정 카메라만 바꾸면 **비슷한 가격에 코너 검출 정밀도가 오른다.**
   D455로 바꾸는 것은 깊이 스펙만 오르고 color 해상도는 그대로라 **우리에겐 효과가 없다.**
2. **논문의 sub-mm 수치를 우리 2~3 mm와 나란히 적지 않는다.** R12·R14·C8·C9는 계측기 등급이 다르다.
   비교표를 만들 때는 **센서 열을 반드시 같이 넣는다.**
3. **기여 주장의 축은 "고정 멀티캠 + 손목캠 + 독립 GT" 조합이다.** 정확도 절대값이 아니다.
   §5의 빈칸이 그 근거이고, R3를 가장 성실하게 인용·비교해야 한다.
4. **장수 방어 논리는 이미 확보돼 있다.** 45 event는 R2(15장)·R5(25자세)보다 많다.
